# ADR 0015：证据必须留痕、脱敏，并有保留上限

状态：已批准
日期：2026-09-14

## 背景

ADR 0013 让验收依赖可执行判据，ADR 0014 让状态写入原子且可恢复。两者都建立在「证据可信」之上，但此前有三种情况会让证据不可信或不可持续：

1. 实现范围快照会静默跳过超大文件、超出上限的目录，`complete` 只能靠猜；
2. journal、verification 报告、命令输出会落盘，可能把 token、连接串口令写进长期留存的文本；
3. journal 与 runtime 证据随运行时长无限增长，长跑项目最终会被自己的证据拖垮。

## 决策

1. 快照必须留痕：被跳过的路径记录为 omission（路径、原因、大小），`complete` 只在没有任何 omission 时为 true。
2. omission 明细有上限（200 条），超出后折叠为计数与哈希，保证「跳过的东西变没变」仍可判断。
3. omission 的严重级别可配置：`scope.omission_policy` 为 `warn`（默认）或 `fail`。
4. 证据落盘前必须脱敏，且分两档：提示词只用高置信规则（避免误伤 spec 里的契约示例），落盘的 journal / 报告 / 命令输出额外启用通用键值规则。
5. 证据必须有上限：journal 超过阈值自动轮转并保留一代（`.1.jsonl`），读取时把历史与当前拼回完整序列。
6. 清理必须显式且可预演：`change gc` 默认只输出计划，`--apply` 才执行；删的只能是 `.cometflow/runtime/` 下可重新推导的内容，绝不触碰 `changes/`、`specs/`、`.cometflow-history/`。

## 理由

- 「没比对过」和「没越界」是两件事，静默跳过会让门禁给出虚假的安全感。
- 脱敏若一刀切会破坏 spec 的契约文本；分档是唯一能同时满足「不误伤」和「不漏」的做法。
- 证据的价值随时间衰减，但体积只增不减；保留上限是让长跑可用的必要条件。
- 删除必须可预演、可解释、范围可证明，否则清理本身就会变成一次数据事故。

## 后果

- `change scope` 会多出 omitted 段；快照不完整时 `complete=false`。
- 命令输出与验证理由在落盘时会被改写，出现 `***redacted***` 属预期。
- 归档后的 change 会失去 `impl-baseline.json`（`change gc --apply` 之后），因此无法再对历史 change 重算实现范围；这是刻意的取舍：历史结论保留在 journal 与 verification 里。
- journal 轮转后，`readChangeJournal` 默认只返回最近 2000 条事件，完整序列需要显式提高 limit。
