# ADR 0020：UI 编辑 spec 的语义——保存即版本，草稿只有 change 提案一种形态

状态：已批准（决策已定，实现随 [web-ui-followup-plan.md](../plan/web-ui-followup-plan.md) 的 N5 落地）
日期：2026-09-14
关联：ADR 0001（spec 单一事实源）、ADR 0012（spec 版本即产物）、ADR 0007（UI 只走 headless service）

## 背景

Web 端的 spec 编辑器保存时会立刻 `refreshSpecBaseline`：每次保存都是一次 canonical 版本变更 + lock 刷新。
这个语义是诚实的（内容变了就是新版本），但界面没有配套的「改之前看一眼」与「改错了回得去」，
于是误编辑的代价直接落在契约上。需要把语义定下来，而不是给界面加一个平行的草稿存储。

## 决策

1. **界面不引入第二事实源。** 默认语义保持「保存即一次版本」：任何内容变化都在版本链上留痕。
2. **提交前可预览变更。** 编辑器提供「预览变更」，展示相对当前版本的 unified diff（数据来自版本仓），
   确认后才写入。
3. **可撤销。** 提供「撤销到上一版」，等价于 `spec restore <path>@<上一版>`，复用 ADR 0012 的版本仓，
   不新增回滚机制。
4. **草稿只有一种形态：change 的提案 spec**（`changes/<change>/specs/`，由 `readProposedSpecs` 读取，
   `spec diff --impact --change` 可预演影响）。一键存提案必须满足：
   - 目标 change 已存在且处于 **shape** 阶段（提案的语义就是「这个 change 打算改成什么」）；
   - 路径固定为 `changes/<change>/specs/<相对路径>`，不新增存储；
   - 界面明确标注「这不改 canonical spec，归档时才应用」。
5. **反向可见。** 编辑器打开某份 spec 时，若已存在提案版本，顶部提示「当前有提案（change X）」，
   并提供与该提案的 diff 入口。

## 理由

- 平行的草稿存储会变成第二事实源，直接违反 ADR 0001：又要回答「哪份才是真的」，而这个问题本不该存在。
- 版本链已经能表达「改了什么」；缺的只是「改之前看一眼」与「改错了能回去」，这两件事都不需要新存储。
- 提案机制早已存在（`readProposedSpecs` + 影响分析），缺的是 UI 入口；补入口比造新机制便宜且不会分叉语义。

## 后果

- 保存 spec 永远等于「一次契约变更」；界面必须把这件事说清楚（展示 diff 与将要产生的新版本号）。
- 误编辑的恢复路径是 `restore`（可逆、留痕），而不是「撤销草稿」。
- change 成为「改契约」的唯一入口形态，shape 阶段的使用频率会上升。
- 断言 `changes/<change>/specs/` 是唯一草稿形态之后，`spec validate` / 影响分析不需要认识任何新目录。
