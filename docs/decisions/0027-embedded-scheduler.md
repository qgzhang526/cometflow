# 0027 serve 内嵌调度器：以 job 托管、单实例租约、常驻状态写进项目配置

状态：已批准（2026-09-17）
关联：[0026 daemon 进程归属](./0026-daemon-process-ownership.md)（本条修订其结论）、
[0024 调度器持久性](./0024-scheduler-durability.md)、[0021 并发写保护](./0021-concurrent-write-protection.md)、
[daemon-drives-change-plan.md](../plan/daemon-drives-change-plan.md)、
[scheduler-concurrency-plan.md](../plan/scheduler-concurrency-plan.md)

## 背景

P4 把 daemon 变成了交付流水线，但"无人值守"仍有一个断点：**它必须由人在终端启动，而且 serve 一重启就没了**。
用户的期望是"人写完 COMETFLOW.md 与 specs，后面交给它常驻推进"，同时在页面上看得见、控得住。

直接让浏览器 spawn 一个游离进程是 ADR 0026 明确否掉的；剩下的问题是：**进程归谁、常驻怎么表达、冲突怎么挡**。

## 决策

1. **serve 内嵌调度器**：`POST /scheduler/daemon/start` 在 serve 进程内以 **job** 的形式跑
   `runDaemonLoop`（job kind = `daemon`）。日志出口从 stdout 换成 job 日志（SSE + 落盘 + 任务中心），
   于是"调度器在干什么"与其它长任务完全同构。
2. **单实例租约**（`runtime/daemon.lease.json`）：持有者每 10s 刷新心跳，超过 60s 未刷新视为崩溃遗留、
   可被接管。CLI 与内嵌**共用这一把锁**——第二个启动者被拒绝并显示持有者（pid@host / mode / 起始时间），
   而不是排队等（与 ADR 0021 的立场一致）。C1 的"任务领取原子化"只保证不重复跑同一条任务，
   租约才让"一个调度器"成立。
3. **常驻 = 项目配置 `scheduler.autostart`**：页面上的「启动」把它置 `true`，serve 启动时按它自动恢复；
   「停止」置 `false`（停止 = 不再常驻）。CLI 的 `daemon start / stop` **不读也不写**这个开关——
   它是手动/调试通道，不改变"这个项目要不要常驻"的意图。
4. **`manual` 模式不进循环**：它只做一次回收/快照/状态投影就结束。旧实现在没有预算时会无限空转，
   CLI 上看得见，内嵌就成了永不结束的 job。

## 后果

正面：

- "常驻无人值守"闭环：启动一次，serve 重启会自动恢复；日志与停止都在页面上；
- 冲突可解释：谁在跑、为什么不让你再起一个，命令行与页面都能看到同一句话（来自租约）；
- 与 CLI 零分叉：两条路调用同一个循环、同一把租约，只有日志出口与进程归属不同。

负面与边界：

- serve 成为调度器的宿主：serve 崩了调度器也停（靠租约过期 + 下次启动恢复兜底，不是无缝接管）；
- 一个项目在**一台机器上同时只有一个**调度器；跨机器的并发目前没有（那需要分布式锁，超出本批范围）；
- `autostart` 是项目级意图，随项目目录走：换台机器打开同一个项目，它也会按这份意图常驻。

## 与既有机制的关系

| 机制 | 关系 |
|---|---|
| ADR 0026（进程归属 / 控制文件） | 被本条修订：进程主人从"CLI"扩成"托管它的进程（CLI 或 serve）"；暂停/继续/停止仍只写控制文件，语义不变 |
| ADR 0024（租约 / 回收） | 同源思想：调度器的存在也是一个租约，心跳 = 活着，过期 = 可接管 |
| C1 原子领取 | 保留：租约解决"只有一个调度器"，C1 解决"不会选中同一条任务"，两者互补 |
| 任务中心 | 内嵌调度器就是一个 job：`daemon` kind，结果里带 `reason` 与 `iterations` |
