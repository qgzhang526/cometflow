# ADR 0014：状态写入必须原子，迁移必须可恢复

状态：已批准
日期：2026-09-14

## 背景

ADR 0012 让 spec 成为可回放的产物，ADR 0013 让验收成为可执行的判据。但这两条都建立在同一个前提上：状态文件本身是可信的。

在此之前，CometFlow 的所有状态写入都是 `fs.writeFile`，阶段迁移是「算出新状态 → 覆盖写」：

- 写入过程中被杀，会读到截断的 `comet-state.yaml` / `task-plan.yaml` / spec 版本 blob；
- 状态写完但记账（journal、spec 版本）未完成时，崩溃后无法区分「没开始」和「做了一半」；
- 手工编辑机器生成文件没有任何检测手段，破坏是不可见的；
- Windows 上并发读取会让 `rename` 返回 EPERM，实现上必须处理。

## 决策

1. 所有状态写入走原子写入：写临时文件 → fsync → rename → 同步目录；失败时清理临时文件并保留旧内容。
2. rename 做有界重试：Windows 在目标被读取时会返回 EPERM/EBUSY，按退避重试而不是直接失败。
3. 阶段迁移走两阶段提交：prepare（落盘待提交记录）→ 写状态 → 记账 → 清记录；读取状态前先收敛未完成的迁移。
4. 迁移冲突不猜测：既不等于起始阶段也不等于目标阶段时，保留待提交记录并交由 `doctor` 报错。
5. 结构化状态盖内容哈希：计划与 change 状态写入时盖 `plan_hash` / `state_hash`（带域标签的规范 JSON 哈希），由 `spec verify` 校验；老数据缺字段时降级为跳过。
6. 残留可见：`doctor` 报告残留临时文件与滞留迁移，`doctor --clean-temp` 才删除。

## 理由

- 半写的状态比没有状态更危险：它会被后续逻辑当成事实读入。
- 「先记账再动手」不可能，因为记账本身也可能失败。两阶段提交把不可判定窗口压缩成一条可检测的记录。
- 内容哈希是唯一不需要额外信任的完整性来源：文件格式、缩进、键序都不影响判定。
- 迁移冲突必须由人判断，自动猜测会把一次数据事故变成两次。

## 后果

- 写入路径多一次 rename 与 fsync；状态文件小、写入频率低，代价可接受。
- `readChangeState` 不再是纯读：它会先收敛未完成迁移（最多一次额外文件读加一次原子写）。
- 手工编辑 `task-plan.yaml` / `comet-state.yaml` 会被 `spec verify` 判为 `plan-integrity` / `change-state-integrity` 错误，正确做法是走 CLI。
- 老 change（无实现范围基线）不再被误判为「全仓越界」，而是明确报告「无法判定」。
