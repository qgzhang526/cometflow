## 4. 三个失败演示

原则：成功路径证明「能跑」，失败路径证明「可信」。三个都设计成**可控、可重复、有兜底**。

### 幕一 · 越界被拒

**要证明的**：文件写到声明模块之外会被标 OUTSIDE，验收直接拒。

**现成素材（已核实）**：`D:\zqg\demos\old\cbb-emergency-access` 里已经有一个真实越界案例，`cometflow change scope access-request .` 的输出是：

```text
change: access-request
module: internal/access
baseline: 2026-09-19T08:38:06.388Z
added internal/access/config.go [module-prefix]
added internal/access/model.go [module-prefix]
added internal/access/server.go [module-prefix]
added internal/access/service.go [module-prefix]
added internal/access/store.go [module-prefix]
added internal/app/impl.go [allow-list]
added internal/tunnel/tunnel.go [OUTSIDE]
changes: 7 unattributed: 1
unattributed: internal/tunnel/tunnel.go
```

**做法**：现场照着这个格式造一次。跑 `change run` 之后，用编辑器在模块外新建一个文件（例如 `internal/tunnel/probe.go`），再跑 `change scope`。

**口播**：「Agent 越界是常态，不是意外。这里我手工写了一个模块外的文件来复现它——注意 `[OUTSIDE]` 这一行和最后的 `unattributed: 1`。」

**预期现象**：scope 输出出现 `[OUTSIDE]` 与 `unattributed` 计数；Web 上「变更 → 范围页签」里逐条列出越界文件。

**兜底**：如果没标 OUTSIDE，说明文件落在 allow-list 或模块前缀里，换一个目录再试；同时正好可以讲「allow-list 是用来显式承认共享文件的，不是用来放水的」。

**待彩排核实**：`change verify` 在存在 OUTSIDE 文件时是否直接判 fail，以及界面上的确切文案。

### 幕二 · 判据不过，退回构建

**要证明的**：判定不是打一次分，是一条有退路的流水线；退路有上限。

**做法**：在一个已实现的工单上，把某个实现改坏（例如让 A2 那条判据返回错误码不对），然后跑 `cometflow change verify <name> .`。

**预期现象**：

- CLI 输出里 A1 passed、A2 failed（带 exit code 与 stdout）
- `changes/<name>/verification.md` 里出现 failed 条目
- `comet-state.yaml` 的 `repair_attempts` 从 0 递增（上限 3）
- 阶段回到 build；`change status` 能看出来

**口播**：「注意它没有把这次失败记一笔了事，而是把任务退回了构建阶段。这就是 `verification.md` 里那行 `repair_attempts: 0/3` 的用处。」

**兜底**：如果连续失败到上限，直接进 blocked 停机——这反而是更好的讲解点：「上限到了它就停机找人，而不是一直烧预算。」

**待彩排核实**：verify 失败后 phase 是否确实回到 build；`repair_attempts` 上限值；界面上「验收结论」表的显示。

### 幕三 · 杀掉进程，接着跑

**要证明的**：状态在磁盘上，不在进程里。

**做法**：

1. 启动一次变更执行（`change run <name> . --agent opencode`，或更慢的 Agent）
2. 中途 `Stop-Process -Force` 杀掉，或直接关掉终端
3. `cometflow change status <name> .` → 阶段仍停在 build
4. `cometflow change journal <name> .` → 能看到 `run-started` 后面缺结束事件
5. `cometflow change resume <name> .` → 给出下一步动作（已核实这一命令存在且会输出下一步建议）
6. 重新跑，接着完成

**预期现象**：journal 里 `run-started` 之后没有对应的结束事件；resume 明确指出下一步。

**口播**：「刚才是真的把它杀了。状态没有丢，因为状态不在进程内存里——它在 `comet-state.yaml` 和 `journal.jsonl` 里。」

**兜底**：如果 mock Agent 太快杀不掉，换 `--agent opencode` 或用录屏。

**待彩排核实**：resume 在「构建中被打断」这个场景下的确切输出。

### 三个演示要不要截图

要。每个演示采一张 CLI 输出图 + 一张界面图，放进附录备查页；现场万一失败，直接翻附录说「这是刚才那条命令的执行结果」。
