五个缺口：

1. **没有把设计理念单独讲出来。** 现在观众看到的是一串机制（锚点、冻结、check、范围报告），但没人告诉他们这些机制背后是同一套主张。**听不懂的根源在这里**——机制记住了、主张没记住，回去跟同事复述不出来。
2. **只有「主链路」，没有「压力下的行为」。** 崩溃、并发、重启、漂移、预算耗尽——这些是判断能否上生产的关键。
3. **没有讲一次交付在磁盘上留下了什么。** 这是「工作原理」最直观的证据，也最容易让人产生「我也想要」：越界判得出来、漂移判得出来、结论可复现，靠的都是那几个文件。
4. **没有「怎么开始用」。** 听众最大的疑问是「听起来好，但我怎么在自己的项目里起步」。现在最后一页是「下一步」，讲的是项目未来的开发计划，不是给听众的行动指引。
5. **没有诚实的边界。** 缺「还没做完的」，反而降低可信度。

## 3. 设计理念：两组六条（**已实施，第 9 页**）

这是第二版方案的核心。把 30 条 ADR 收敛成六条主张，分两组——正好能把现在的第 12–22 页一分为二。

### 关于「什么是真的」

| 理念 | 一句话 | 落地成什么 | 代价（要诚实讲） |
|---|---|---|---|
| ① **规格即契约，不是文档** | 代码质量的根本是规格质量 | 锚点、12 类契约、引用单向、25 条校验规则 | 写规格的成本前置到开工前 |
| ② **单一事实源** | 一个事实只定义一次；人只写两个地方 | 使命文件 + `specs/`；其余全是机器投影，不可手改 | 有些文件你必须接受「不能编辑」 |
| ③ **契约先于实现** | 判据先红后绿，冻结即快照 | 冻结绑版本与 hash；执行阶段不再重新解释规格 | 需求变了要走重新冻结，比随手改慢 |

### 关于「谁说了算」

| 理念 | 一句话 | 落地成什么 | 代价 |
|---|---|---|---|
| ④ **生成与评价分离** | 判定权不在实现者手里 | check > document > agent 的优先级；独立 Verifier | 多一道验证的资源开销 |
| ⑤ **确定性优先** | 能推导的，不用模型推 | 拆解是纯代码：任务 = 锚点，可重复生成 | 补不了你没写的锚点 |
| ⑥ **有界自主** | 不是无限自主，是带着边界跑 | 预算跨重启、修复循环上限、准入检查、停机等人 | 无人值守会遇到需要人介入的停点 |

页面做法：两列各三条，每条一行理念 + 一行「它换来了什么」。然后在后续每一页的角落标上「理念 ①」这样的编号，让听众能一路对回这张图。**这是让整场汇报被记住的关键动作。**

理念出处：`docs/design/001` 的七条融合原则、`docs/design/002` 的内核原则。

## 4. 工作原理：讲透四条链路（新增 3 页，其中 1 条并入现有页）

「工作原理」不是再加机制名词，而是把四条链路完整走一遍，每条链路上都摆真实产物。

**链路一 · 任务从哪来（新增 1 页）**
`使命里的目标` → `spec 里的锚点` → `任务清单` → `工单`。
关键点：每一环都是推导，不是模型生成。同一份 spec 生成一百遍结果一样，没有「拆解幻觉」。这是理念 ⑤ 的落地。

**链路二 · 契约怎么固化（并入现有第 16 页「冻结到底冻了什么」，不新增）**
`改 spec` → `登记版本` → `冻结快照（文件 hash + 锚点 hash + 模块 + 验收项）` → `执行阶段不再重新解释`。
加厚方式：第 14 页「冻结到底冻了什么」的文字换成真实 `comet-state.yaml`，让「冻结」有个实物。（**已做**）

**链路三 · 判定怎么执行（新增 1 页）**
`跑 check` → `优先级 check > document > agent` → `不过就退回构建` → `有界修复` → `连续无进展停机等人`。
关键点：判定不是一次打分，是一条有退路的流水线；退路有上限，上限到了就停机找人。这是理念 ④ 和 ⑥ 的落地。

**链路四 · 证据怎么沉淀（新增 1 页）**
就是上面那七个文件的目录树：左边目录树，右边一列「它回答什么问题」。
为什么越界判得出来 → `impl-baseline.json`；为什么漂移判得出来 → `spec-baseline.json`；为什么结论可复现 → `acceptance-checks.json` 带命令和退出码；为什么记录改不了 → `journal.jsonl` 是追加式的。
**这一页是整套方案里最值得做的一页**：它对「工作原理」的说明力最强，也最容易让人产生「我也想在我的项目里看到这些」。

## 9. 其他优化建议

时间放开之后，可以从「讲清楚」升级到「让人信服」。以下按四个方向分。

### 9.1 叙事层：给全场一根主线

**A. 一条贯穿全场的追问。** 现在 deck 是「三件事」的并列结构，缺一个从头追到尾的问题。建议就用：**「我凭什么相信一个 Agent 说它做完了？」** 后面的每一页都是这个问题的答案——判据是答案、判定来源是答案、冻结是答案、范围报告是答案、有界修复也是答案。有主线，听众才跟得住。

**B. 一套施工类比贯穿到底。** 这套系统的每个概念都能对上一件事：

| 系统里的东西 | 类比 |
|---|---|
| spec | 设计图纸 + 合同 |
| 锚点 | 图纸上的一条工程项 |
| check 判据 | 验收标准 |
| change | 施工单 |
| 冻结 | 图纸会审封版 |
| 独立 Verifier | 监理 |
| 验收 | 竣工验收 |
| 归档 | 竣工备案 |
| 范围报告 | 施工范围核对 |
| 写保护守卫 | 门禁 |

非工程背景的听众靠这一套能一次听懂，工程背景的听众会觉得这个概念映射本身就是设计质量的证据。

**C. 症状与机制对回去。** 第 2 页列了四个症状（改动不可控、上下文会丢、验收靠人、没法托管）。在后续机制页的角落标「症状 ①」这样的编号，配合理念编号，听众能一路对回开场。**编号系统不要超过两套**，否则变成噪音。

**D. 主动提出三个最强反驳。** 与其等人问，不如自己摆出来：

1. 「这不就是多加了一层流程吗？」
2. 「写了没人维护怎么办？」
3. **「模型变强了，这套还需要吗？」**——这是技术听众心里最强的疑问，不主动回答，他们会带着怀疑听完。

第 3 条的答案建议：模型越强，写得越多越快，判定权和事实源越重要——因为「快」放大的是错误的传播速度。契约的意义不随生成能力提升而消失。

**E. 同一个案例贯穿到底。** 现在案例是分散的。改成 CBB 应急接入一个案子从第 2 页讲到最后一页，每页引用它的同一批数字，收尾给一张「这个案子的完整账本」。

### 9.2 结构层：补图、补边界、补坐标

**F. 三张缺失的图。**（**已实施**：第 6 页流水线、第 15 页目录树、第 18 页状态机与数据流）原来只有一条流水线，其余全是文字页。建议补：

1. change 状态机图（shape → build → verify → archive，含「验收不过退回构建」那条回边）
2. 判定链路的数据流图（判据从 spec 抽出来 → 跑命令 → 结论带来源 → 写进账本）
3. 目录结构树（第 4 节「链路四」那张磁盘账本页可以用它）

**G. 完整术语表。** 第 4 页现在只有 5 个词，系统实际有 20 多个：spec、锚点、判据、变更、验收、冻结、基线、漂移、准入、租约、修复循环、归档、门禁、投影、lock、version、verdict、scope、verifier、eval、evolve。建议正文保留一页概念地图，附录放完整术语表。

**H. 「什么时候不该用」一页。** 探索性原型、一次性脚本、接口还在剧烈变化的领域、没人愿意写规格的团队。**这一页比任何优势页都更能建立信任**，也是防止听众误用的必要内容。

**I. 定位坐标页。** 技术听众一定会拿它跟熟悉的东西比，不给坐标他们会用错误的参照物判断：

| 熟悉的参照物 | 关系 |
|---|---|
| Cursor / Claude Code | 帮你写；这套管写完之后怎么判定和留痕 |
| Spec Kit / 规范文档 | 规范形态；这套要求契约可判定、可派生任务 |
| CI/CD | 代码的流水线；这套是交付的流水线 |
| Terraform | 基础设施的期望态；这套是软件模块的期望态 |

**J. 按角色给阅读路径。** 一页索引：写规格的人看哪几页，跑 Agent 的人看哪几页，平台维护者看哪几页，评审者看哪几页。

### 9.3 证据层：从「能跑」升级到「可信」

**K. 自举——已决定不做（2026-09-20）。**

核实结果：本项目自己没有用 CometFlow 管自己——仓库根目录没有 `COMETFLOW.md`、没有 `specs/`、没有 `.cometflow/`。

决定：**不体现自举，也不为此改造代码。** 处理方式：

- 正文与讲稿都不提「我们用自己开发」这类说法；
- 如果有人直接问起，如实回答：平台还在快速变化，种子期自举有循环依赖，目前用的是实验项目（CBB、todoscan）做验证；
- 把这条放进附录「已知缺陷与未实现清单」，与其它诚实清单并列。

**L. 现场演失败，而不是演成功。** 现在五个桥段都是成功路径。成功路径证明「能跑」，失败路径才证明「可信」。建议换掉其中一到两个：

1. 让 Agent 故意改到模块之外 → 范围报告标 OUTSIDE、验收拒绝
2. 让判据不过 → 任务退回构建、进入修复循环、连着几轮没进展就停机
3. 中途杀掉进程再启动 → `change resume` 接着跑（正好演示「状态在磁盘上」）

**M. 20 分钟可复现包。** 仓库里已经有 6 个实验项目（todoscan、2048、stardust-outpost、cbb-emergency-access 等）。挑最干净的一个做成上手包：一条命令建环境 + 一页指引 + 第一条件跑绿的预期输出。附录里放路径，听众带得走、当场就能试。

**N. 度量基线页。** 把项目自己的数字集中成一页：100 个测试文件 / 约 580 条用例 / 30 条 ADR / 演示案子的 18 条判据 / 7 个文件 0 越界 / 真实 Agent 的 114 与 124 秒。每个数字标一句「这是怎么算出来的」。

### 9.4 表达层：为答问和带走做准备

**O. 备注里加跳转提示。** 每页备注末尾写「如果被问到 X，翻附录 A3」。答问时不用现场找。

**P. 术语读音统一。** spec / check / anchor / change / verdict / scope 这些词中英混读容易乱，定一套读法写进讲稿。

**Q. 会后速查卡。** 把整场汇报压成一张 A4：一张流程图 + 六条理念 + 三个命令。让听众带走能贴在工位上——这是汇报结束后唯一还会被看的东西。

**R. 附录最后一页放「问题 → 看哪份文档」索引。** 有人问「哪份文档讲 X」，一眼能找到。

### 9.5 形态建议

**S. 双轨制。** 时间不限的话，最有说服力的形态是上半场 + 下半场：

- 上半场 60–70 分钟：讲透原理（理念 + 四条链路 + 三个失败演示 + 边界）
- 下半场 30–40 分钟：现场工作坊，用听众自己的一个真实小需求走一遍 generate → freeze → run

工作坊是唯一能让人真正确信的方式——他们亲眼看到自己的需求被跑通。

**T. 三层可裁剪版本。** 一套内容做三个深度：15 分钟精简版 / 45 分钟标准版 / 90 分钟完整版（含工作坊），附录共享。同一份材料能在不同场合复用，也方便以后每次只改一层。

## 10. 如果只能再做四件事

按「对『讲透彻』的贡献 ÷ 成本」排：

1. **自举，或者诚实地说明没有自举**（K）。成本可高可低，但它决定整场汇报的可信度上限。
2. **把失败演示加进去**（L）。两小时的工作量，换来从「能跑」到「可信」的跃迁。
3. **施工类比 + 一条主线追问**（A + B）。几乎零成本，直接决定听众能不能听懂并复述出去。
4. **三张结构图**（F）。把连续六页的文字页变成可看的结构，理解成本立刻下降。
