## 第 1 页 · 封面

*时间：0:00–0:20*

各位好，今天我用 CometFlow 这个项目做汇报。
先用一句话说它是干什么的：把 AI 写出来的代码，做成能交付的东西。
后面四十五分钟分两段。前面讲它怎么做到这件事，后面直接在浏览器里跑一个真实项目给你们看。

## 第 2 页 · 今天怎么讲

*时间：0:20–1:00*

先说一下今天的内容安排，免得大家听的时候不知道重点在哪。
前二十多分钟讲做法和几个关键机制，中间我会说清楚这套东西不解决什么问题，避免把预期抬得太高。
后半段打开 Web 工作台，用一个 Go 写的应急运维接入项目走一遍完整流程，从契约校验一直到归档门禁，全部在浏览器里点，不敲命令行。
PPT 上出现的数字，都是这台机器上真跑出来的，不是我估的。

## 第 3 页 · 先把几个词说清楚

*时间：1:00–4:00*

在讲做法之前，先把后面会反复出现的几个词说清楚，都是很朴素的东西。
spec，规格，就是一个模块该做什么的说明书。我们这份说明书放在 specs 目录里，人和机器都读它。
锚点，就是说明书里的一个小标题。比如「POST 申请接口」这样一行。一个锚点对应一件要做的事，所以它也是任务的来源。
check，判据，就是一条能跑的命令。比如「跑一下这个测试，看结果是不是通过」。有它，对错就不用靠人吵。
变更，一次改动的工作区。从开工到归档，中间所有证据都留在这一个目录里。
验收，就是拿判据去核对这次改动，结论由机器给出，不由写代码的人自己说。

## 第 4 页 · vibe coding 的第二公里

*时间：4:00–6:30*

先说为什么要做这个东西。
Vibe coding 的第一公里体验很好，半小时能出一个能跑的原型，这是真实的好处。问题出在第二公里。
第一个症状是改动不可控。你让它改一个接口，它顺手重构了三个文件，你说不出哪些改动是必要的。
第二个症状是上下文会丢。上一轮明确说过不要动数据库，这一轮它又动了，因为上一轮的决定没有留在任何地方。
第三个症状是验收靠人。交付前有人得把功能点一遍，改一次点一次，改十次还是点一遍。
最后一个症状是没法托管。想让它晚上自己跑，不敢，因为没有任何东西能拦住它说一句「我做完了」。

## 第 5 页 · 卡住的是哪一段

*时间：6:30–8:00*

所以卡住的是哪一段？这张页想把这个边界划清楚。
模型能力这一段，这个项目帮不上忙，它不换模型，也不替你把提示词写好。需求本身没想清楚，它也帮不上忙，规格写得含糊，后面的判据一定也是含糊的。
它管的是中间那一段，从「写完了」到「可交付」。具体三件事。
第一，这次改动到底改了哪些文件，边界在哪，越界了没有。
第二，什么叫做对了，这句话要能被机器执行，而不是靠人点头。
第三，人不在场的时候，怎么让它自己跑，而且跑不飞。
整场汇报都围绕这三件事。

## 第 6 页 · 做法

*时间：8:00–9:30*

做法其实就是一句话：人写规格，Agent 实现，机器判卷。
请留意这里的分工。规格由人写，这是人的责任，跑不掉。实现交给 Agent，这块是可替换的。判定这一步既不给写规格的人，也不给写代码的 Agent，而是交给机器。
为什么要这么分？因为前两个角色都有动机说自己做完了，只有判定这一步必须是没有立场的。

## 第 7 页 · 人类只写两个地方

*时间：9:30–11:30*

第一个机制，单一事实源。规则很硬：人只写两个地方。
一个是项目使命文件，写清楚使命、技术栈，以及每个目标的范围、成功标准和非目标。另一个是 specs 目录，项目的全部契约。
除此之外，目标投影、计划、规格锁、索引、任务队列，全部是机器生成的，不允许手工编辑。
这一条的价值在于影响面可以计算。比如一个错误码只在错误码目录里定义一次，其它地方只能引用，不能重述。改了名字，所有引用它的地方会被立刻揪出来，这个等下演示里会看到。

## 第 8 页 · 契约长什么样：一个接口就是一个锚点

*时间：11:30–13:00*

第二个机制，契约里的任务来源是明确的。
这页是 specs 目录里 access 这个能力的真实片段。一个接口就是一个二级标题，这个标题就是锚点。任务不是人列的，是从锚点派出来的。
每个接口下面列清楚它用哪些错误码、哪些状态码、属于哪个模块，以及验收条目。这些不是给人看的说明文字，是被解析器读的结构。
所以不允许出现「用户登录相关」这种自由文本，因为它派生不出任务，也校验不了。

## 第 9 页 · 每条验收都要能跑

*时间：13:00–15:00*

第三条，验收必须能跑。这是整个平台里我觉得最关键的一条约束。
这页是界面上「验收覆盖」页签的真实截图。上面写着：未覆盖 0，验收项 18，可执行 check 18。也就是说这个项目里十八条验收，每一条都挂了一个能执行的命令。
比如 A1 是申请提交后返回 200 并生成待审批的申请单，右边就是它的执行命令。这个项目是 Go 写的，所以命令是 go test 加一条用例名。
写不出 check 的验收不会被偷偷放过，界面上会单独标出来，因为它没法进无人值守模式。

## 第 10 页 · 从目标到任务：拆解不调用模型

*时间：15:00–16:30*

契约写完之后，从目标到任务这一步，不需要调用模型。这一页是计划面板的真实截图。
左边选目标，上面一排是生成、校验、评审、批准、冻结。下面是这个目标派生出来的任务，每条都标了接口标题、能力、绑定的 spec 文件和行号，以及状态。
这里三个目标一共派生出八个任务，覆盖十八条验收。这八个任务没有一条是人手写的。
评审和批准这两步是留给人的，因为我们不希望拆解这件事完全交给机器自说自话。

## 第 11 页 · 冻结到底冻了什么

*时间：16:30–18:00*

冻结这一步具体冻结了什么，这页说得最清楚，这是变更详情页的真实截图。
四个阶段的进度条在顶上：确认验收、构建、验收、归档，现在停在构建。
下面这张表是这次任务的契约快照。绑定的锚点是 access 里那个申请接口，规格版本 v1，规格哈希是 d457 开头的那一串，模块边界是 src/access，验收项是 A1、A2、A3。
这些值一旦冻结，执行阶段就不再重新解释规格了。需求变了怎么办？先在 specs 里改，重新冻结，再开新的工单。这样每个结论都能对回到一个确定的契约版本。

## 第 12 页 · 实现之前，判据是红的

*时间：18:00–20:00*

接下来是执行。这一页想讲的是「不可自证完成」。
先说现在的状态：这个项目里没有实现代码，所以判据此刻是红的。红的不是事故，是设计意图，契约和判据本来就先于实现。
这里有个细节值得说一句。在 Web 界面上，「验收」这个按钮现在点不动，因为任务还在构建阶段，没进入验收阶段。也就是说流程上不给「跳过实现直接宣布通过」留口子。
判据由谁跑、跑了什么、结果是什么，都在流水里留着记录，改不了。

## 第 13 页 · 谁说了算：判定来源标在方括号里

*时间：20:00–21:30*

那到底谁说了算？这一页列了三种判定来源，界面上把来源标在方括号里。
check 表示结论来自规格里的可执行判据，这是机器事实，权重最高。document 表示来自人工或独立复核的结论文档。agent 表示由独立的验证 Agent 给出。
下面这三行是刚才那次真实运行的输出。三行都以 check 结尾，说明结论是跑出来的，不是 Agent 自己宣布的。
如果一个任务实现没到位，验收会把任务退回构建阶段，进入修复循环。连续几轮没有进展，平台会停机等人介入，而不是一直烧预算。

## 第 14 页 · 改动边界：越界就拒绝

*时间：21:30–23:00*

这一页是模块边界，也是我在实际使用里最看重的一条。
每个能力在规格里声明自己的实现落在哪个模块。跨能力共享的文件，比如服务入口和存储层，要在项目使命文件的模块归属里显式声明，不能随口说这是公共代码。
任务跑完会出一份实现范围报告，列出每个改动文件的归属：模块内、模块前缀、允许清单，还是越界。越界的改动会被直接拒绝。
这份报告在界面上就能看到：变更 → 选中这次改动 → 范围页签。页面上写清楚模块是哪个、扫描了多少文件、哪些路径允许越界，以及越界文件的逐条清单。
左边那次真实实现改了七个文件，越界零个。多个 Agent 并行的时候，冲突的任务按模块串行，不会互相覆盖。

## 第 15 页 · 无人值守：顺序和准入都写在明面上

*时间：23:00–24:30*

最后一条机制是无人值守。这页是调度面板的真实截图。
左上角是队列和已用预算，预算跨重启累计。中间是调度器最近一次决策，现在显示的是没有调度器在跑。右下角是控制区，启动、暂停、继续、停止，这四个按钮在浏览器里就能点。
这一页下半部分是队列内容，八条任务按顺序排开，每条显示调度状态、来源、交付到哪个变更、尝试次数。
顺序不是随机排的。调度顺序写在项目使命文件里，这里是 G1、G2、G3，因为 G2 的通道要用 G1 发出来的授权。另外有一条准入检查：如果某个任务的验收根本没法自动判定，调度器会直接停机，把预算留给人去补判据。

## 第 16 页 · 一次真实交付的账

*时间：24:30–26:00*

把前面讲的东西合起来看一遍账。这页是最普通的一张表，但每个数字都是跑出来的。
真实 Agent 完成一个任务，两次分别是一百一十四秒和一百二十四秒，三条判据全过。剩下的任务用 mock 加参考实现跑，十四秒跑完八个。十八条判据全过，首次通过率百分之百，锚点覆盖率八比八，漂移零，门禁检查通过。
我想强调的不是这些数字好看，而是它们是机器算出来的。换个人来跑一遍，结论应该一样，这才是把个人技巧变成团队能力的关键。

## 第 17 页 · 演示怎么走

*时间：26:00–27:30*

接下来是演示。演示环境是两个项目，都在这台机器上。
左边这个是现场要跑的，三个目标已经冻结，八个任务待办，还没有实现代码。右边这个是提前跑完的，八条任务全部交付，十八条判据全过，门禁通过，作为兜底。
今天全部在浏览器里点，不敲命令行。五个桥段：契约校验、拆解、跑 Builder、启动调度器、看账本和门禁。
如果现场 Agent 卡住，我们随时切到兜底项目，流程一样能走完。

## 第 18 页 · 演示一　契约可校验

*时间：27:30–29:00*

第一个桥段，契约可校验。
（打开 规格 → 影响与门禁 → 校验引用）现在跑一遍校验，结果是 OK，一致性门禁零条 finding，没有漂移。
（打开 规格 → Spec 文件 → 编辑 tunnel/spec.md）现在我把这条引用改成一个不存在的错误码。注意，还没保存，编辑器底部已经从「引用全部可解析」变成「一条未解析」，这一行也标红了。
这里顺便分清一件事：errors.md 里那些是定义，这一行是引用。改定义不报错，改引用才报错；反过来，定义被改坏时，受伤的是引用它的那些文件。同一个改名动作，改在哪一处，现象完全不同。
保存，回到 影响与门禁，再校验一遍。报出来了：引用的错误码在错误码目录里找不到。
这就是契约和文档的区别。改坏一个名字，不用等人评审，机器立刻就能发现。
（把名字改回去，确认重新 OK）

（打开 调度）这里有启动调度器按钮。它起的是服务内嵌的一个调度任务，日志进任务中心，重启服务还会自动恢复。

## 第 22 页 · 演示五　账本与门禁

*时间：41:00–42:30*

最后一个桥段，看账本和门禁。
（切到兜底项目 → 总览）总览有三块。项目状态和计划变更，能看到三个目标全部冻结、八个变更全部归档。
问题清单，和命令行的门禁检查是同一份投影，现在零条错误零条警告。
质量与健康度，首次通过率、验收可执行率、锚点覆盖率、漂移，都在这里，而且是按门禁阈值显示的。
（点 门禁卡）逐项结论列出来：规格校验、一致性检查、健康检查、任务计划校验、指标阈值、基线对比，全部通过。
这里说的「和 CI 是同一份实现」，意思是判断这些项过不过的代码只有一份，放在领域层里。命令行调的、界面上点的、CI 里跑的，都是同一份代码；CI 那边只是一个很薄的壳，负责把命令跑起来。所以本地看到的结论，就是流水线会得到的结论。反过来才危险：如果 CI 自己另写一套脚本，两边会慢慢不一致，看着在拦，其实没拦住。

## 第 23 页 · 现场会故意犯的五个错

*时间：42:30–44:00*

讲完流程，再花两分钟说反过来的事：这些机制到底能拦住什么。
我准备了五个会故意犯的错，它们落在流程的不同位置。
第一个，把错误码的名字改掉。规格校验立刻报「引用了不存在的错误码」，拦住。
第二个，某条验收只写一句「应该正常工作」，不挂命令。界面会把这条标成不可执行；无人值守也会因为判不了而停下来，不白跑。
第三个，改到模块之外的文件。范围报告会把那个文件标成越界，验收直接拒绝。
第四个，还没实现就想点验收。流程上过不去：任务还在构建阶段，验收按钮是灰的。
第五个，让 Agent 自己说做完了。这条最典型：判据仍然是红的，任务被打回构建阶段，它的话不算数。
这五条合起来是一句话：流程上不给「看着像完成」留位置。

## 第 24 页 · 改一次 spec：从 v1 到 v2

*时间：44:00–45:00*

最后一个补充，也是最贴近真实工作的一件事：规格改了怎么办。
现在项目里所有规格都是 v1。假设我们发现空闲超时定成五分钟不合理，应该改成三分钟。
步骤是这样：先在规格里改这一处，再跑校验，然后让它算出影响面，也就是哪些已经冻结的任务绑着这份规格、会被波及。
接着重新冻结计划，把受影响的任务重新绑到新版本；再开一个新工单去做这次改动，验收通过后归档，规格就从 v1 变成 v2。
这里有一条硬规矩：执行过程中不允许再解释规格。想让 Agent 按新写法做，就必须先把规格改掉、重新冻结，再开工单。
好处是每一份交付都能对回到一个确定的规格版本。半年后有人问「当时那个超时为什么是五分钟」，答案不在聊天记录里，在版本历史里。

## 第 25 页 · 还没做完的

*时间：*

该说的地方也说完，说一下还没做完的部分，免得给后面接手的人挖坑。
第一，拆解审核里高风险识别的规则还没实现。现在配了高风险策略会回落到人工审核，停在草稿等人批，行为是安全的，但没达到设计意图。
第二，写保护的 hook 目前只有 claude-code 这一个平台支持安装，另外两个平台会明确报不支持，不会假装装上。
第三，Web 界面上「验收」按钮只在验收阶段可点，构建阶段点不动。好处是堵住了跳过实现的口子，代价是没法手工把任务推到验收阶段，只能通过运行 Builder 或者命令行。
第四条是环境相关：演示项目不是 git 仓库，所以 git 来源校验这一环会跳过，真实项目里它会要求工作区已提交、历史没有漂移。

## 第 26 页 · 下一步

*时间：*

最后是下一步，三件具体的事。
先把高风险拆解审核的规则补上，让计划评审能真正按风险分级。
再把写保护的 hook 扩展到 opencode 和 codex，让越界写入在工具层就被拦下，而不是等到验收阶段才被发现。
然后找一个真实项目跑一段无人值守，把度量基线积累起来。现在这些数字来自演示项目，还不足以回答「它到底省了多少人」。
资料在 docs 目录里，使用说明、演示脚本和今天的方案都在。我的汇报到这里，谢谢大家。

## 附一：演示等待期间的口播（桥段三专用）

Agent 真跑通常需要约 2 分钟。等待时按顺序使用下面几句，避免冷场。

- Agent 现在拿到的是冻结版本的规格段落，加上这个任务的三条验收。它不需要猜我们要什么。
- 注意它判断的依据：规格里写了来源地址不在白名单时要拒绝，所以判据 A3 就是测这个行为。契约和判据是一一对应的。
- 这段时间也可以看任务中心：job 的状态和耗时在里面。日志只有三行摘要，Agent 的原始输出平台没有采集——这是有意的，判定要的证据在验收和流水里，不在它自己的控制台输出里。
- 如果它这次只实现了一半，我们接下来会看到判据仍然是红的，任务被退回构建阶段。那就是这套设计想要的效果：不接受自述。
